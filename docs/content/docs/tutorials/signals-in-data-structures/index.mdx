---
title: Signals in Data Structures
description: Encapsulate signals inside classes or closures — they power reactive capabilities while remaining hidden from the public surface
---

In [Composing Signals](/docs/tutorials/composing-signals) the state was a plain object of [Signals](/docs/api/signal). That works well, but sometimes a class or another data structure is the more natural way to model your domain - a counter, a booking, a list of stays - and you still want it to be reactive. Turning every field into a public `Signal{:ts}` is inconvenient there. In this tutorial you'll put the Signals inside such data structures, so they stay reactive while their users just call methods, and they still plug into React and into other signals.

**Prerequisites:** Complete [Composing Signals](/docs/tutorials/composing-signals) and [Nesting Signals](/docs/tutorials/nesting-signals) first.

## The Counter class

The `Counter{:ts}` keeps its value in a private `Signal{:ts}` and takes care of its limits - nothing outside the class can push it past `min{:ts}` or `max{:ts}`.

<include lang="ts" meta='title="counter/state.ts"'>./counter/state.example.ts#code</include>

Every method that reads the `Signal{:ts}` - `value{:ts}`, `canDecrement{:ts}`, `canIncrement{:ts}` - accepts a [`Monitor`](/docs/concepts/fundamentals#why-monitors-exist) and passes it along. That's what keeps the class reactive while the `Signal{:ts}` stays hidden: the caller decides who is listening. Methods that only write don't need one.

## Composing data structures

A `Stay{:ts}` groups a rooms `Counter{:ts}` and a nights `Counter{:ts}`, so everything about one `Stay{:ts}` lives in one object. It also receives a `StayParent{:ts}` - just the part of the `Booking{:ts}` it needs to remove itself - so it can answer `canRemove{:ts}` and `remove{:ts}` without anyone passing the `Booking{:ts}` around.

<include lang="ts" meta='title="stay/state.ts"'>./stay/state.example.ts#code</include>

<Callout>`StayParent{:ts}` is a showcase of how far plain JavaScript can take you, because Signals keep working inside any object graph you build. It isn't a pattern your application has to follow. Passing a `canRemove{:ts}` boolean and an `onRemove{:ts}` callback down as props is just as valid, and often the simpler choice.</Callout>

A `Booking{:ts}` owns the list of `Stay{:ts}` objects and implements `StayParent{:ts}`. It takes care of adding and removing them - it never lets the last one go. The totals are reactive for free: whatever they read through the monitor is what they depend on, including stays added later.

<include lang="ts" meta='title="booking.ts"'>./booking.example.ts#code</include>

You may not even have noticed that a `Booking{:ts}` is a nested `Signal{:ts}`: it holds a `Signal{:ts}` of `Stay{:ts}` objects, and every `Stay{:ts}` encapsulates Signals inside its `Counter{:ts}` objects. That's the point - you define data structures the way you want, without thinking about reactivity, and the Signals API shows up only where a value is read, where the types enforce passing the monitor around.

## Wiring React components

In this tutorial the components never touch a `Signal{:ts}` - that is a choice, not a rule. They call methods, and every read needs a monitor, so TypeScript won't let you bypass reactivity by accident.

## Closures work too

A class is one way to hide Signals; a function closure is another. The convention is the same - reading methods take a monitor:

```ts title="counter/create-counter.ts"
import { type Monitor, Signal } from "@owanturist/signal"

export function createCounter(min: number, max: number) {
  const count = Signal(min)

  return {
    value: (monitor: Monitor) => count.read(monitor),
    increment: () => {
      count.write((current) => Math.min(current + 1, max))
    },
    decrement: () => {
      count.write((current) => Math.max(current - 1, min))
    },
  }
}
```

The Signal lives in the closure and can't be reached from outside. Pick whichever style fits your codebase.

## Going further [#going-further]

<Callout type="idea">
**Advanced:** instead of naming the reading method yourself, a class can implement [`ReadableSignal`](/docs/api/signal#readable-signal-type) - an interface with a single `read(monitor){:ts}` method - or [`WritableSignal`](/docs/api/signal#writable-signal-type) when it also has `write{:ts}`. Anything that accepts a readable or writable signal then accepts your class out of the box: [`useComputed`](/docs/api/use-computed), [`untracked`](/docs/api/untracked), the getter of a [derived signal](/docs/api/signal#derived-readonly), and so on. This tutorial uses plain methods to keep the public surface exactly what you chose - reach for the interfaces when you want the class to be interchangeable with a Signal.
</Callout>

## Testing the data structure

Because the rules sit inside the class, you can test them without React. The `monitor` fixture is covered in [Testing Signals](/docs/tutorials/testing-signals).

```ts title="counter/state.test.ts"
import { expect, it } from "vitest"

import { Counter } from "./state"

it("stays within its bounds", ({ monitor }) => {
  const counter = new Counter(1, 3)

  counter.decrement()
  expect(counter.value(monitor)).toBe(1)
  expect(counter.canDecrement(monitor)).toBe(false)

  counter.increment()
  counter.increment()
  counter.increment()
  expect(counter.value(monitor)).toBe(3)
  expect(counter.canIncrement(monitor)).toBe(false)
})
```
